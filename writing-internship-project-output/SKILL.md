# 实习项目产出写作

## 概览

这个 Skill 用于把真实项目证据整理成中文实习项目产出、简历项目经历和面试话术。核心原则是：先看证据，再提炼故事；先保证真实性，再追求表达效果。

## 工作流

1. **先收集证据**：阅读用户提供的说明、项目文件、README、设计文档、任务记录、入口代码、配置、脚本、测试和已有产出。证据不足时照常输出草稿，但把不确定内容放入“待补充信息”。
2. **识别项目故事**：提炼真实问题、业务/团队背景、使用者、旧方案痛点、没有该工作的风险。
3. **选择 4-5 个技术亮点**：每个亮点必须满足“问题背景 -> 技术方案 -> 收益”，不要把普通功能点包装成亮点。
4. **生成完整产出**：新写完整文档时使用 `references/output-structure.md`。
5. **匹配表达风格**：使用 `references/style-guide.md` 控制语气、颗粒度和措辞边界。
6. **生成简历和面试材料**：使用 `references/resume-bullets.md` 压缩简历 bullet，扩展技术深挖问题和面试话术。
7. **补充真实场景坑点**：当用户要求“开发中遇到的问题”“真实问题”“联调问题”“vibe coding 难点”“项目复盘”时，优先整理需求澄清、联调字段、业务口径、测试样例、配置发布、AI 生成方案纠偏等真实落地问题；不要只输出代码审查式 bug 清单。
8. **证据自检**：最终使用 `references/evidence-checklist.md` 检查所有业务规模、个人贡献、上线状态、性能指标和实现细节；无法证明的指标删除或移入“待补充信息”。

## Reference Routing

- 新建完整项目产出：读取 `references/output-structure.md`。
- 匹配既有实习产出风格：读取 `references/style-guide.md`。
- 生成简历段落、面试话术、深挖问题或避坑提醒：读取 `references/resume-bullets.md`。
- 声称业务规模、个人角色、上线状态、性能收益或实现细节前：读取 `references/evidence-checklist.md`。
- 用户要求开发复盘、真实困难、联调坑、vibe coding 难点或项目踩坑时：按本文“真实场景坑点写法”组织内容。

## 输出规则

- 默认使用中文 Markdown。
- 使用真实机制、类名、配置名、脚本名、文件名或系统名；没有证据不要发明。
- 不要声称“主导”“独立负责”“已上线”“提升 X%”“日均 QPS”等，除非用户或仓库证据支持。
- 有价值但未证实的内容放入“待补充信息”，不要写进简历 bullet。
- 简历 bullet 要短，技术深挖可以展开；不要把所有深挖细节塞进简历。
- 简历 bullet 中可以保留少量关键类名、策略名、协议名或对象名来增强专业度，但不要堆叠 `BO/DTO/PO`、参数对象、返回对象和长串实现类；深挖文档再展开完整类名。
- 对受限系统、非公开接口、账号、Cookie、Token 和不可公开地址保持脱敏。

## 输出验收

生成完整项目产出、项目总结或评测样稿后，必须在最终输出前用验收脚本检查是否覆盖工作流要求：

```bash
python scripts/validate_output.py <output.md> --strict
```

如果用户要求“不要生成文档、直接在对话里给我”，也要先把拟输出内容写入临时 Markdown 文件，运行验收脚本，再把通过验收的内容发给用户。

验收失败时，必须根据脚本报告继续修改内容，补齐缺失工作流项或删除风险表述，然后重新运行验收脚本；未通过前不要发送最终答案。若只生成简历 bullet 或局部面试话术，可不使用 `--strict`，但仍要运行脚本检查风险表述。

## 真实场景坑点写法

当用户要求总结“开发时可能遇到的真实问题”时，先判断用户要的是哪一类问题：

- **代码审查类问题**：安全漏洞、并发 bug、缓存一致性、异常处理、性能风险。
- **开发/联调现场问题**：需求口径不清、上游字段缺失或含义不一致、前后端展示协议不一致、测试样例覆盖不足、配置发布/回滚口径不清、AI 生成方案能跑但不贴合老系统边界。

如果用户强调“真实场景”“联调”“vibe coding”“攻破难点”，优先写第二类。每个问题建议用以下结构：

```markdown
### <问题标题>

**现场问题**:
<开发或联调现场怎么暴露出来，不要只写代码缺陷。>

**容易卡住的点**:
- <需求/字段/配置/展示/测试/AI 生成方案中的具体卡点>

**最后沉淀的做法**:
<如何把口径、样例、配置、边界或实现方案固定下来。>

面试表达:
> <一段可以直接讲给面试官的复盘话术。>
```

常见真实场景坑点方向：

- 业务给的是截图、PDF、表格或自然语言文案，需要先拆成可配置规则、字段、优先级和命中关系。
- 联调字段不齐或含义不一致，例如 SKU 属性缺失、枚举取值不止一种、字段名和预期不一致。
- 多规则命中、去重、拼接、排序需要靠真实样例逼出口径。
- 空结果也是合法结果，需要和调用方确认协议，不要把未命中写成接口失败。
- 配置中心的 JSON 能保存不代表表达式、脚本或规则能编译和命中，需要补配置校验和回滚口径。
- AI/vibe coding 生成的初版方案可能只覆盖主流程，需人工校准项目分层、入口边界、降级语义、字段约定和测试矩阵。
- 测试不要只覆盖代码分支，要覆盖业务组合、边界样例和联调展示效果。

## 质量判定口径

产出质量不看篇幅，看是否同时满足：

| 维度 | 合格标准 |
| --- | --- |
| 证据真实性 | 每个核心亮点都能回到代码、文档或用户描述。 |
| 技术亮点 | 不是功能罗列，而是有问题、机制和收益。 |
| 简历可用性 | bullet 能直接压缩进简历，且没有无法自证的夸张表述。 |
| 面试可讲性 | 面试官追问“怎么做、为什么这么做、边界是什么”时有机制可讲。 |
| 真实复盘性 | 开发问题能回到需求澄清、联调口径、配置验证、测试样例或 AI 方案纠偏等真实场景，而不只是泛泛说“遇到 bug”。 |
| 风险控制 | 不泄露敏感信息，不写未经确认的数字、上线状态和个人贡献。 |

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 只描述功能点 | 改成“问题背景 -> 技术方案 -> 收益”。 |
| 堆 AI/Java buzzword | 绑定到真实机制、文件、配置或脚本。 |
| 编造指标 | 删除或标为待补充。 |
| 夸大个人贡献 | 用“参与”“负责其中模块”“设计并实现某机制”等可自证表述。 |
| 产出越写越长 | 简历段落压缩，深度内容放到面试储备。 |
| 简历 bullet 堆满 BO/DTO/PO 和实现类 | 只保留 1-3 个最能支撑亮点的关键名词，其余放到技术深挖或源码定位。 |
| 用户要真实联调问题却输出代码审查清单 | 改成需求口径、字段对齐、配置验证、展示协议、测试样例、AI 生成方案纠偏等开发现场问题。 |

