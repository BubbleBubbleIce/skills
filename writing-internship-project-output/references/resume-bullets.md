# 简历段落与面试话术

## 简历段落生成规则

简历段落要从完整产出中压缩出来,不要把所有细节都塞进去。

默认格式:

```markdown
### <项目名> - <一句技术定位>

**技术栈**:<压缩技术栈>

**项目细节**:

- **<亮点 1>**:<问题/机制/收益压缩为 2-4 行。>
- **<亮点 2>**:<同上。>
- **<亮点 3>**:<同上。>
- **<亮点 4>**:<同上。>
```

## Bullet 质量标准

每条 bullet 应包含:

- 技术动作:设计/实现/抽象/接入/封装/优化/隔离/沉淀。
- 具体机制:策略模式、线程池、缓存、Sink、Advisor、规则表达式、校验脚本、配置管理等。
- 工程价值:扩展性、稳定性、可维护性、上下文节省、关键流程保护、质量闸门。

## 具体名词取舍

简历 bullet 需要一点真实名词支撑专业度,但不能变成源码清单。

建议保留:

- 1-3 个最能证明机制的关键类名、策略名、协议名、配置名或平台名。
- 能直接支撑亮点的对象名,例如统一意图对象、核心卡片 DTO、XML 协议名。
- 对外可解释的系统名或框架名,例如 Spring AI、Reactor、AutoBots、DUCC。

建议移到技术深挖:

- 长串 `BO/DTO/PO`、Param、Response、Converter、Mapper。
- 只体现数据搬运的对象名。
- 一次 bullet 中连续列多个实现类、枚举、配置类。

取舍口径:

```markdown
好:
- **实现两阶段模型调用的意图识别与执行分发**:通过 Spring AI `ChatClient` 将用户 query 识别为医保一级意图,沉淀为统一 `ChatIntentBO`;再按意图路由到对应 AutoBots Agent 生成流式回答。

差:
- **实现两阶段模型调用的意图识别与执行分发**:通过 `YbUserInitiateConversationHandleStrategy.intentRecognition()` 调用 `YbAgent.getYbIntentRecognitionAgent()` 得到 `IntentResponseBO`,再由 `ChatIntentParser.parseIntentForYb()` 转成 `ChatIntentBO`,最后由 `IntentImplementationStrategyFactory` 分发到 `PaymentFailedIntentStrategy`。
```

每条 bullet 避免:

- 只有"负责开发某功能"。
- 只有"提高效率、提升性能"。
- 讲太多业务背景。
- 写无法解释的组织黑话或项目黑话。

## 技术深挖问题

按项目类型选择问题:

### AI / Agent / Skill 项目

- 为什么要做 Agent/Skill,而不是普通脚本或普通文档?
- 主会话和子任务如何分工?
- 如何控制上下文污染?
- 如何保证输出质量和可复用性?
- 如果模型输出不稳定,怎么约束?

### 后端 / 规则引擎项目

- 为什么不用 if-else?
- 规则如何配置、缓存和热更新?
- 动态执行如何隔离故障域?
- 超时、降级、反压怎么设计?
- 如何避免关键流程被补充能力拖慢?

### 流式 / 响应式项目

- 为什么使用流式响应?
- 冷流和热流如何配合?
- 多通道数据如何合并?
- 异步副作用如何收口?
- 如何处理半截协议标签或流结束 flush?

## 30 秒介绍模板

```markdown
> 在实习期间,我参与了 <业务/平台> 中的 <项目名>。这个项目主要解决 <业务问题>。技术上我重点负责/参与了 <核心模块>,通过 <机制 1>、<机制 2> 和 <机制 3> 解决了 <技术难点>,最终让这个能力在 <扩展性/稳定性/维护成本/用户体验> 上更可控。
```

## 避坑提醒模板

```markdown
**避坑提醒**:
- 不要说"<可能夸大的说法>",更准确是"<稳妥表述>"。
- 没有真实数据时,不要写具体百分比或 QPS。
- 如果被问到 <风险点>,主动说明 <边界/降级/校验/权限控制>。
```
