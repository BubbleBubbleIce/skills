# 证据与真实性检查清单

写实习项目产出前,先确认哪些信息有证据。没有证据的内容不要硬写进亮点或简历。

## 可作为证据的材料

- 用户明确描述。
- 代码文件、类名、方法名、配置项、测试。
- README、设计文档、接口文档、任务记录。
- commit、PR、评审记录。
- 真实运行日志、压测结果、监控截图。
- 已有简历、评审反馈或修改建议。

## 必须谨慎的内容

| 内容 | 处理方式 |
| --- | --- |
| 业务量级、QPS、DAU、命中率 | 没有证据就放入"待补充信息"。 |
| 性能提升百分比 | 没有基线和测量方法就不要写。 |
| 上线状态 | 不确定时写"开发/联调/灰度状态待确认"。 |
| 个人贡献 | 不确定时用"参与"或"负责其中模块"。 |
| 受限系统名 | 注意对外简历是否允许出现。 |
| 敏感接口地址、非公开域名、账号信息 | 不写入最终文档。 |

## 自检问题

完成初稿后逐条检查:

1. 每个核心亮点是否能在代码、文档或用户描述中找到依据?
2. 是否把普通功能包装成了技术亮点?
3. 是否有无法证明的数字?
4. 是否夸大了个人角色?
5. 是否泄露敏感信息或不可公开系统信息?
6. 面试官追问"你怎么实现的"时,是否有具体机制可讲?
7. 面试官追问"为什么这么设计"时,是否能回到业务背景或工程约束?
8. 简历 bullet 是否比技术深挖更精炼?

## 信息不足时

不要停止输出。先生成可用草稿,并在"待补充信息"中列出需要用户确认的项。

推荐写法:

```markdown
| 可量化指标 | 接口耗时、规则数量、覆盖场景等需要根据真实数据补充 |
```

不要写:

```markdown
提升性能 80%,支撑千万级流量。
```
